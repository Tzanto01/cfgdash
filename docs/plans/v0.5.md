# Plan: v0.5 (fleet, start at login, cfgdash settings, config assistant)

Owner: department lead. Status: decisions taken by Nico on 2026-11-02 (all four recommendations); team start waits for his go. Source: Nico, 2026-11-02.

## 1. Multi-machine (ROADMAP 1)

Recommended: cfgdash-native over the tailnet; no T3 fork.

- **Discovery:** every machine that runs cfgdash with `--tailnet` is a peer. A new Fleet view (under *Machine*) lists peers from `tailscale status --json` and probes each one's `/api/v1/health`.
- **Peer auth:** peers fetch each other's `/api/v1/snapshot` and `/api/v1/findings` with a whois-verified identity instead of the per-run token. Only Nico's own devices are accepted (his login, or a tagged device of his tailnet), it is read-only, and each machine opts in. This needs the `tcp:7820` tailnet grant (Nico's ACL change, still open since 2026-10-28) and a new contract `fleet-v1`.
- **Views:**
  - Side by side and drift first: rows that differ between machines, keyed by collector, block and row ids.
  - Each machine's health counts.
  - Compare against an earlier `cfgdash export` of the same machine. This needs no peer auth, so it ships first.
- **T3 route (not recommended now):** forking T3 to reuse its connected environments means maintaining a fork of a fast-moving app. cfgdash would then only work inside that fork. If T3 later supports plugins or panels, a thin panel that embeds each machine's cfgdash is the cheap version of this idea.

## 2. Start at login (opt-in)

- `cfgdash autostart on|off|status` plus a toggle in cfgdash settings (section 3). Off by default.
  - Windows: a per-user logon entry (HKCU Run key or a user scheduled task, no admin).
  - Linux: a systemd user unit (`~/.config/systemd/user/cfgdash.service`).
- An autostarted instance runs with `--no-open`, warms the snapshot cache at start and has no idle shutdown. Running `cfgdash` while it is alive opens the browser on the live URL instead of printing it. Autostart is localhost only; `--tailnet` stays a separate choice, which also covers section 1.
- This writes outside the cache dir (the logon entry or unit file). It is a new narrow exception to the read-only rule in `AGENTS.md`, which records the exceptions Nico accepted.

## 3. Settings: one place for harness settings, a real gear for cfgdash

- The top-right "Settings" link opens the harness settings editor, which duplicates the Settings view on the left.
- **Recommended:**
  - Fold editing into the Settings view itself. An "Edit" toggle turns each row's value into its control, with the scope switch (User / Project / Local) and Restore default. Review and Apply keep the edits-v1 diff and confirm flow.
  - The gear becomes **cfgdash settings**: start at login, theme, default folder, tailnet publish, fleet opt-in, assistant model and effort.
- cfgdash settings live in its own config file (`%APPDATA%\cfgdash\config.json` / `~/.config/cfgdash/config.json`), written only by cfgdash. `overrides.json` stays hand-edited.

## 4. Config assistant (ROADMAP 9)

- **Side panel chat:**
  - It knows what is selected or mentioned: rows, files and health findings, always redacted.
  - It can explain, suggest and propose a fix.
  - A proposed fix becomes a normal edits-v1 proposal (diff, then confirm, then audit). The model never applies anything itself.
- **Full check:** one button runs a review of the whole harness for the current folder. It starts from the health findings and returns a ranked list of suggestions, each with a proposal where one is possible.
- **Model and effort:** picked in the panel, with defaults in cfgdash settings.
- **Runtime (recommended): a live Claude Code session.**
  - cfgdash starts `claude --print --input-format stream-json --output-format stream-json --model <m> --effort <e>` in the target dir, keeps the process alive while the panel is open and streams each message in. This is a real multi-turn session with a warm prompt cache, under Nico's existing Claude login (no API key in cfgdash).
  - When the panel reopens, `--resume <session-id>` continues the session.
  - **Fallback:** a headless `claude -p --resume <id>` per message. It keeps the history, and the cache stays warm while messages come within the cache window.
- **Containment:**
  - The session gets no built-in file, shell or web tools. It gets only a cfgdash MCP server with these tools:
    - `get_snapshot`, `get_findings`, `get_file`: redacted, never-read rules apply
    - `propose_change`: creates a proposal only
  - Localhost listener only, never on the tailnet, same rule as `/api/v2`.
  - Needs Claude Code installed and logged in on that machine; otherwise the panel says why.
- **Security:** needs its own `assistant-v1` contract and a `security-reviewer` pass before code (ROADMAP 9 already says so).

## 5. Extras (Nico, 2026-11-02)

- **Undo an applied change:** `POST /api/v2/audit/{auditId}/revert` makes a normal edits-v1 proposal that restores that apply's backups. It is stale if a file changed since that apply (sha256 differs from that apply's `sha256After`), and it goes through the same diff and confirm. The change log in the Settings view gets an "Undo" per entry. Team `platform`.
- **Folder context command (ROADMAP 11):** `cfgdash context --dir <path> [--json]`: instruction chain, effective settings with source, agents, skills, hooks and MCP servers, all redacted. Its builder is shared with the assistant's context blocks. Team `assistant`.
- **Browser tests in CI:** a Playwright job that runs on every push. It starts the published exe against a synthetic harness in a temp dir, walks the main views, does one edit (propose, apply, undo) in a temp project scope, and checks the CSP and that no request leaves the cfgdash origin. Team `web`, last.
- **Cross-tool drift rules (health-v1, additive):** the same MCP server defined differently across Claude Code, Codex and OpenCode (`mcp-drift`, info). An instruction file that one tool loads for the folder and another does not (`instructions-drift`, info). A tool's config is present but fails to parse (`error`, warning, already covered). Team `fleet` (shares the diff logic).
- **Security fixes left open from v0.4 (team `platform`):**
  - Windows 8.3 short names are expanded before the never-read rules run.
  - Windows link targets on UNC paths are never probed.
  - OpenCode's data dir honors `XDG_DATA_HOME` (`XDG_DATA_HOME` is added to the env allowlist as a `Runtime` name).

## Decisions (Nico, 2026-11-02)

1. Multi-machine: cfgdash over the tailnet, export compare first. No T3 fork.
2. Assistant write scope: the edits-v1 catalog only. For instruction, agent, skill and hook files it explains and suggests text that Nico applies by hand.
3. Assistant runtime: a live Claude Code session (stream-json, resumable).
4. Settings: editing folds into the Settings view, and the gear opens cfgdash's own settings.

Still Nico's: the `tcp:7820` tailnet grant for peer access (section 1).

Contracts: [cfgdash-config-v1](../contracts/cfgdash-config-v1.md), [fleet-v1](../contracts/fleet-v1.md), [assistant-v1](../contracts/assistant-v1.md); the edits-v1 UI section moves into the Settings view.
